# Threat model and current controls

Scope: one assessment workspace with admins, members, one WooCommerce store and registered MCP servers. This file distinguishes code/chart controls from runtime-verified controls. A local or production values file alone does not prove the target cluster enforces its NetworkPolicies.

| Threat | Current control | Limit / verification |
| --- | --- | --- |
| Committed or leaked secrets | Random local values in ignored mode-0600 `.local/credentials.json`; Kubernetes Secret references; no credentials in Helm values | Kubernetes Secret encryption at rest is not enabled by this local k3s setup. Do not record or commit the local credentials file. |
| Stolen/revoked member key | Random key secret, HMAC digest in PostgreSQL, constant-time comparison, key/user status read on every MCP HTTP request | A caller with a still-active key can act through all tools granted to that member. Revoke promptly. |
| Dashboard CSRF/session theft | Separate hashed session token, HttpOnly + SameSite=Strict cookie, CSRF token on mutations; Secure enabled in production values | Local HTTP cookies are not Secure. HTTPS/TLS must be configured for production. Session expiry is fixed; session rotation/password recovery is not implemented. |
| Member uses shared upstream credential beyond intended role | Upstream credential is encrypted server-side; members receive only granted tools; grant checked in both catalog and call path; Woo service key is dedicated | A granted tool acts with its shared credential. Member grants are role-wide, not per-user/argument-level. WooCommerce MCP limits data projection but the service API key is read/write for product creation and status updates. |
| Client key reaches upstream | Gateway constructs an independent upstream request with the stored static credential; incoming bearer/cookies are not copied | Malicious upstreams still receive tool arguments and the credential configured for that server. Use least-privilege upstream credentials. |
| Admin registers an SSRF destination | IP literals, local-only names, external HTTP and URL credentials rejected; allowlisted cluster Service hosts supported; external DNS answers must be public; redirects disabled; DNS rechecked before new sessions; NetworkPolicy restricts gateway egress | DNS check and HTTP resolution are separate, so code does not pin a resolved IP. NetworkPolicy excludes private/loopback/link-local IPv4 as a second boundary. Validate CNI enforcement on the cluster; do not claim DNS-rebinding immunity. |
| Malicious or compromised MCP server | Per-server credential; per-server session/timeout; schemas and outputs bounded; no retries; server error is isolated; chat tool calls still pass current gateway authorization; tool descriptions/results are labeled untrusted in the system prompt | A model can still be influenced by malicious descriptions or results. The gateway remains the authorization boundary. Chat writes do not currently require a second user confirmation. |
| Duplicate or uncertain write | Audit intent commits before dispatch; one server call is serialized; no automatic tool retry; timeout/transport break after dispatch recorded `unknown_outcome` | Exactly-once execution is not claimed. The user must reconcile the upstream state before retrying. |
| One member acts on another | Database-derived principal, per-user key ownership, audit snapshots, member audit filtering; admins can revoke keys; chat's short-lived signed assertion is minted only from the current session and revalidates its WebSession and active user on every MCP request | Admins can view workspace member keys' metadata and revoke them, but cannot recover their secret. Dashboard chat history is held in browser memory and is not server-persisted. |
| Model provider receives sensitive store data | Provider URL/model are operator-configured; its optional key comes from Kubernetes Secret; browser never receives the key; chat sends only permission-filtered tool schemas and results needed for the active turn | The configured provider receives the user's prompts, bounded recent text history, tool schemas and tool results. Review provider data handling before sending real customer data; demo data is synthetic. |
| Trace previews reveal customer data | Content capture is deployment-configurable, disabled in production values and enabled only in local synthetic-data values; sensitive field names, emails, phone-like numbers, bearer strings, known token patterns and URL queries are redacted; preview fields are bounded and cleared after a short TTL; hidden reasoning and system prompts are never captured | Redaction is heuristic and can miss free-form names, addresses or uncommon secrets. Any captured content remains sensitive. Do not enable with real customer data until encryption, consent, access and deletion policies have been reviewed. Investigation metadata/findings do not yet have an independent retention policy. |
| Investigation prompt injection or fabricated findings | Trace content is untrusted, analysis has no tools, sample size/output are bounded, and saved evidence must cite a selected trace and exact quote from its source step; investigation APIs are admin-only | The analysis model can still make inaccurate summaries or recommendations. Treat findings as operator suggestions, verify linked evidence, and do not let findings grant access or execute changes. |
| Unexpected investigation spend or duplicate analysis | Run requires a server-side model and explicit price, records usage and estimated cost, applies a conservative token-based per-run preflight cap, accepts an idempotency key, and marks interrupted provider work unknown without automatic replay | Provider tokenization and billing may differ from estimates. A timeout or worker crash can have unknown cost even when findings were not saved; monthly aggregate budgets and provider-side limits remain future work. |
| Gateway or upstream compromise reaches Kubernetes API | Custom gateway/dashboard/demo MCP pods disable service-account token mounting, run non-root, read-only root filesystem, drop capabilities; namespace NetworkPolicies | Local negative tests confirmed blocked access to MariaDB, PostgreSQL, WordPress and WooCommerce MCP. The metrics-only scraper ingress rule has not passed a live pod-to-pod check in local k3d. Database and WordPress images use vendor entrypoints; no claim they run fully non-root. |
| Data/schema loss during upgrade | PostgreSQL, MariaDB and WordPress use PVCs; Alembic versioned migrations; chart/image tags are configurable | Single-node local-path storage is not HA or backup. Helm rollback does not restore database state. Snapshot/backup and restore must be practiced before production. |

## Audit contents

The gateway records principal email/user ID when known, API-key ID (null for session-authenticated chat), server/tool snapshot, correlation ID, start/end, duration, outcome and error category. It stores an intent before allowed upstream dispatch. Agent traces also store model/provider, selected route and reason, token usage, configured-rate cost estimates, status and duration for each model/tool step. Metadata-only capture does not store content. When enabled by deployment policy, traces may retain short redacted user/assistant/tool previews for the configured TTL; this can still contain sensitive data. System prompts and hidden reasoning are not captured. Investigation jobs store selected trace IDs, expected behavior/checks, findings, supporting quotes and analysis usage/cost; they are admin-only, but that metadata does not yet have its own retention policy. API key secrets, chat assertions and upstream credentials are never logged. Authentication rejections with no resolvable identity are logged as unknown callers; no token is logged.

## State to verify in the demo

Use two distinct user accounts and API keys. Show that a member cannot call a denied tool directly even if they know its public name; revoke a key and call `/mcp` again; disable a server and re-list/call; interrupt one upstream while exercising a healthy one; inspect audit attribution. With a model configured, demonstrate that chat sees only the signed-in user's tools and that each chat tool call is attributed to that user. Explain that provider prompts/results leave the cluster, the provider key stays in a Kubernetes Secret, and a signed-in user can influence their own supplied chat context but cannot bypass gateway grants. Then run `./scripts/verify-network.sh` with the dedicated `.local/kubeconfig` and record the actual result.
